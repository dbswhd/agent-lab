# Room Ideation — 효용 평가 프로토콜 (RI-01)

> **작성:** 2026-09-12 · **상태:** 프로토콜 확정, **결과 미측정**
> **소유 범위:** 아이디어 구체화 Room(idea lane)의 사례 수집 방법·비교 절차·판정표.
> **소유하지 않음:** 제품 범위와 구현 순서는 [ROOM-IDEATION-PLAN-2026-09.md](../ROOM-IDEATION-PLAN-2026-09.md)가 소유한다. 기존 episode/grader 계약([EVAL-CONTRACT.md](../EVAL-CONTRACT.md))은 이 문서로 대체되지 않는다.
> **결과 파일:** `docs/evals/room-ideation-results.md` (RI-14에서 생성, 아직 없음).

이 문서는 **사용자 한 명의 재사용 여부**를 판정하기 위한 것이다. 6개 사례로 통계적 우위를 주장하지 않는다.

---

## 1. 사례 집합

- **총 6건.** 사용자의 실제 아이디어만 사용한다. 모델이 만든 가상의 아이디어는 사용자 평가 입력으로 쓰지 않는다.
- **개발용 3건 (`holdout: false`)** — RI-02~RI-06 개발 중 관찰과 Checkpoint A 판정에 사용.
- **확인용 3건 (`holdout: true`)** — RI-14 전까지 **열지 않는다**. 개발 중 프롬프트 튜닝에 사용 금지.
- 다음 세 조건이 최소 한 건씩 포함돼야 한다:
  - `repo_state: none` — 연결된 레포 없음 (순수 개념).
  - `repo_state: existing` — 기존 레포가 있고 변경 지점을 확인해야 함.
  - `constraint_shift: true` — 진행 도중 시간·플랫폼·범위 제약이 바뀌는 사례.

### 익명화

`evals/ideation_cases.jsonl`은 커밋된다. 따라서 각 사례에서 다음을 제거하거나 치환한다:

- 실명·회사명·고객명·계정 식별자 → 역할 명사 (`팀`, `거래처`, `사용자 A`).
- 비공개 레포 경로·URL → `repo_state`와 일반화된 설명으로 대체.
- 금액·계약 조건 등 민감 수치 → 자릿수만 유지한 근사치 또는 제거.

익명화가 **아이디어의 제약을 바꾸면** 그 사례는 쓰지 않는다. 제약이 사례의 핵심이기 때문이다.

---

## 2. `evals/ideation_cases.jsonl` 스키마

한 줄 = 한 사례. JSONL이라 주석을 담을 수 없으므로 스키마는 이 문서가 권위다.

| 필드 | 타입 | 의미 |
|---|---|---|
| `case_id` | `str` | `RI-CASE-01` … 안정 식별자. 재사용·재번호 금지 |
| `holdout` | `bool` | `true`면 RI-14까지 열지 않음 |
| `seed` | `str` | 사용자가 실제로 입력할 **원문 그대로의 막연한 개념**. 사후에 다듬지 않는다 |
| `desired_change` | `str` | 사용자가 원하는 변화 (한 줄) |
| `constraints` | `str[]` | 시간·플랫폼·비용·취향 등 실제 제약 |
| `repo_state` | `"none" \| "existing"` | 레포 연결 여부 |
| `repo_hint` | `str \| null` | `existing`일 때 익명화된 레포 성격 설명 |
| `constraint_shift` | `str \| null` | 도중에 바꿀 제약. 없으면 `null` |
| `notes` | `str \| null` | 익명화로 잃은 맥락 등 |

측정값(점수·시간·비용)은 이 파일에 쓰지 않는다. 결과는 `room-ideation-results.md`에 쌓는다.

### 현재 상태

**사례 0건 — 미수집.** `evals/ideation_cases.jsonl`은 현재 비어 있다. 수집은 사용자만 할 수 있으며(§1 익명화), 그전까지 RI-01은 닫히지 않는다. 이 상태에서 Checkpoint A와 RI-14 기준 충족을 주장하지 않는다.

## 3. 비교 절차 (A/B)

- **A = native 단일 에이전트.** 사용자가 평소 쓰는 도구에, 목적과 "좋은 계획"의 기준을 **충분히** 전달한다. 약한 프롬프트를 baseline으로 만들지 않는다.
- **B = Agent Lab idea lane Room.**
- 같은 `seed`·`constraints`·자료를 쓴다. A의 출력물을 B에만 제공하지 않는다.
- **실행 순서를 사례마다 번갈아 둔다.** 같은 아이디어를 두 번째로 볼 때의 이점은 실재하므로, 순서와 관찰된 차이를 기록한다.
- **같은 인간 상호작용 시간 상한**을 A와 B에 적용한다 (사례별로 정하고 기록; 권장 20분).
- 모델별 비용·latency 차이는 별도로 기록하고, 품질 차이를 멀티에이전트의 인과 효과라고 단정하지 않는다.
- 후보 초안은 가능하면 도구명을 가리고 읽는다. interactive 과정의 완전한 blind는 불가능하므로 **한계로 기록한다**.
- 모델 judge는 문서 형식·누락 점검 보조로만 쓴다. **효용 판정자는 사용자다.**
- mock 결과 파일과 live 결과 파일을 섞지 않는다. CI는 기존 mock-only 원칙을 유지한다.

---

## 4. 사용자 판정표

사례마다 A와 B 각각에 1~5점 + 구체적인 한 줄 이유.

| 항목 | 확인 질문 |
|---|---|
| 유용한 새 방향 | 원래 생각하지 못했지만 실제 채택할 요소가 나왔는가? |
| 구체성 | 실제 사용 장면과 작동 방식을 설명할 수 있는가? |
| 적합성 | 내 목적·제약·취향을 반영했는가? |
| 착수 가능성 | 첫 작업을 시작하기 위해 다시 설계해야 할 부분이 얼마나 남았는가? |

**추가 기록(사례별):** 사용자 개입 시간 · provider 호출 수와 비용 · 실패/재시도 · 장황해서 버린 출력 · 다음 날 계획을 수정한 범위 · 어느 결과로 실제 작업을 시작했는가.

---

## 5. 운영 기준 (제안)

RI-14에서 다음을 **모두** 충족하면 신규 일반 Room 생성만 idea lane 기본값으로 전환한다:

1. 6건 중 **4건 이상**에서 Room(B) 결과를 선호.
2. 보류한 확인용 3건 중 **2건 이상**에서도 선호.
3. **2건 이상**의 계획으로 실제 외부 개발을 시작.
4. 설정·대화 부담이 위 이익을 상쇄하지 않음.

사용자 사용 시간이 부족하면 **미측정 상태로 유지**한다. 대체 지표를 새로 만들어 판정을 대신하지 않는다.

**기준 미달:** 한 차례 개선 후 재평가. 그래도 이득이 없으면 좋은 prompt/문서 템플릿만 추출하고 전용 Room 개발은 동결한다. 특정 종류의 아이디어에만 효과가 있으면 그 용도로 좁힌다.
